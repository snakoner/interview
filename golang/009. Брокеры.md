### Базовая архитектура Kafka
Kafka - распределённый(данные и нагрузка распределяются между несколькими серверами (брокерами), а не хранятся и обрабатываются на одной машине) журнал событий. Кластер состоит из нескольких broker’ов. Обычно, в кластере 3+ серверов.

```
Kafka Cluster
    |
    +-- Broker 1
    +-- Broker 2
    +-- Broker 3
```

```
Payment Service
    |
    v
topic: payments
    |
    +----------------+
    |                |
    v                v
Accounting      Notifications

Один producer может писать в topic, много сервисов могут независимо читать.
```

#### Topic
Topic — логическая категория сообщений (orders, payments, users).
Например, сообщение {"order_id": 123, "status": "created"} попадает в orders.


#### Partition
Topic состоит из partition, каждая partition — это отдельный лог. Kafka только добавляет данные в конец партиции:
```
orders
├── partition 0
├── partition 1
├── partition 2
```

Партиции нужны, чтобы масштабироваться. Если есть только одна партиция, то читать её может эффективно только 1 consumer. Если N - могут читать N консьюмеров параллельно.

Количество partition задаётся при создании topic.

##### Как выбирается partition
Если нет ключа:
- producer.Send(msg) - Kafka раскидывает сообщения
- producer.Send(Key: userID) - hash(userID) % partitions

Kafka гарантирует порядок сообщений только в одной партиции.

#### Репликация
Есть partition:
```
orders-p0
```

```
replication factor = 3
```

```
Broker1 -> Leader
Broker2 -> Follower
Broker3 -> Follower
```

Follower реплицируют данные с лидера. Если лидер падает, Kafka выбирает нового лидера из актуальных реплик.

###### Leader
Producer пишет только в leader. Consumer тоже читает из leader

Follower нужны для отказоустойчивости.

ISR (In-Sync Replicas) — набор реплик, которые успевают синхронизироваться с лидером.

Можно задать: acks=0 (не ждем, пока запишется в leader), acks=1 (ждем, пока запишется в leader), acks=all (ждем запись в leader + followers)

#### Как работает Consumer Group
Consumer Group позволяет нескольким инстансам одного сервиса параллельно читать топик.
```
Topic: orders
p0
p1
p2
```

```
Группа order-service имеет два consumer
consumer-1
consumer-2
```

Kafka распределяет partition:

```
consumer-1 -> p0,p1
consumer-2 -> p2
```

Каждая partition в рамках одной группы назначается только одному consumer. Поэтому сообщение обрабатывается ровно одним consumer внутри группы.

##### Что такое rebalance?

Rebalance — перераспределение partition между consumer.

Происходит когда:

- consumer появился;
- consumer умер;
- добавили partition;
- изменился состав группы.

```
c1 -> p0
c2 -> p1

// c2 упал
// Kafka перестанет получать heartbeat от c2
// Через некоторое время session.timeout.ms consumer считается умершим, запускается rebalance
// Partition передаются другим consumer группы

c1 -> p0,p1
```


##### Что произойдёт при падении broker’а?

Если на broker был только follower: то ничего критичного, Kafka продолжит работу

Если упал лидер, Kafka выберет нового лидера из ISR, producer и consumer автоматически переключатся.

##### Почему Kafka — это лог, а не очередь?

В очереди сообщение обычно удаляется после чтения.
В Kafka сообщение остаётся в журнале независимо от того, кто его прочитал.
