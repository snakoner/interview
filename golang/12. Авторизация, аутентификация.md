> **Аутентификация** - процесс проверки на подлинность кого-либо (логин / пароль), код 401 - Unauthorized

> **Авторизация** - процесс проверки того, что вы имеете доступ к чему-либо, код 403 - Forbidden

Есть два подхода: сессии и jwt-token

#### Сессии

1. Пользователь вводит логин/пароль
2. Сервер проверяет есть ли такой пользователь в БД
3. Сервер создает session_id и отправляет куки: Set-Cookie: session_id=abc123; HttpOnly; Secure; Path=/; Max-Age=3600
4. Браузер сохраняет Cookie и при следующих запросах автоматически отправляет их серверу.
5. Сервер использует куки (например, для аутентификации).
6. Когда пользователь выходит из системы, сервер удаляет куки и отправляет браузеру запрос на удаление куки.


Сессии хранятся на стороне сервера: БД или кеш (Redis)


### Токены
1. Пользователь вводит логин/пароль
2. Сервер проверяет есть ли такой пользователь в БД
3. Сервер создаёт JWT и отправляет клиенту
4. Клиент хранит JWT (в LocalStorage, куках)
5. Клиент отправляет JWT в заголовке каждого запроса: Authorization: Bearer <jwt-token>
6. Сервер проверяет подпись и срок действия JWT

JWT состоит из трёх частей, разделённых точками (.):

header.payload.signature
- Header (заголовок) – содержит тип токена и алгоритм шифрования:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- Payload (полезная нагрузка) – содержит данные (claims), например, id пользователя и роль:
```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "exp": 1710000000  // срок действия токена (время Unix)
}
```

- Signature (подпись) – защищает токен от подделки:
```
HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  secret-key
)
```


### Сессии vs JWT

Плюсы JWT:
- Без состояния – серверу не нужно хранить сессии
- Быстро – можно использовать в микросервисах
- Поддержка в любых языках

Минусы:
- Невозможно отозвать токен до его истечения
- Payload не шифруется, только подписывается (можно прочитать данные!)
- Большой размер (в сравнении с обычными сессионными ID)
