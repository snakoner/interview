### Прогретый и непрогретый storage
1.	Непрогретый storage (cold storage):
- Первый доступ к storage-слоту в транзакции считается “холодным”.
- Для первого обращения к storage-слоту потребуется больше газа.
2.	Прогретый storage (warmed-up storage):
- Если к одному и тому же storage-слоту обращаются повторно в рамках одной транзакции, этот слот считается “прогретым”.
- Стоимость повторного доступа значительно ниже, поскольку данные уже загружены в кэш.


- 	Первый доступ к storage-слоту (cold access): 2600 газа.
- 	Повторный доступ к тому же storage-слоту (warmed-up access): 100 газа.

### calldata vs memory
#### Что такое calldata и memory
> Calldata:
- Это область памяти, которая используется для передачи данных в функции внешнего вызова (external).
- Данные в calldata являются только для чтения и не могут быть изменены.
- Эта область размещается вне EVM (в аргументах транзакции) и доступна контракту напрямую.
> Memory:
- Это временная область памяти, которая используется для обработки данных во время выполнения функции.
- Данные в memory могут быть изменены, но они исчезают после завершения выполнения функции.
- Memory размещается внутри EVM и требует больше вычислительных ресурсов для управления.

#### Почему calldata дешевле:
1. Отсутствие копирования данных:
- Когда вы используете calldata, данные передаются напрямую из вызова функции (входной транзакции). В отличие от memory, данные не копируются в другую область памяти.
- Если передавать большой массив в функцию, использование memory потребует затрат газа на копирование всех элементов, а с calldata этого не произойдет.
2. Оптимизация для чтения:    
- Данные в calldata предназначены только для чтения, и EVM обрабатывает их более эффективно, чем изменяемые данные в memory.
3. Хранение вне EVM:    
- Данные в calldata физически хранятся за пределами основной памяти контракта, что снижает затраты на их управление.
4. Газовые затраты:    
- В Solidity вызов функции с массивом в calldata дешевле, чем с массивом в memory, поскольку:
- Использование memory добавляет затраты на аллокацию и копирование.
- Данные в calldata уже существуют в оптимальном формате для чтения.

### Transparent, UUPS, Beacon Proxies
#### Transparent Proxy
1. **Механизм**: В Transparent Proxy обновления контролируются через прокси-контракт. Администратор прокси имеет права обновлять адрес реализации, и обычные пользователи не могут взаимодействовать с функциями обновления.
2. **Процесс обновления**:
- Администратор вызывает функцию upgradeTo на прокси-контракте, чтобы обновить его на новый адрес реализации.
- Прокси делегирует все вызовы на адрес реализации (который можно менять).
3. **Преимущества**:
- Простота и ясность. Контроль обновлений находится в руках администратора.
4. **Недостатки**:
- Прокси-контракт включает логику обновлений, что делает его более дорогим по газу и более сложным.

#### UUPS (Universal Upgradeable Proxy Standard)
1. **Механизм**: В UUPS обновления контролируются через саму реализацию. Прокси не содержит сложной логики для обновления, а процесс обновления осуществляется через функцию в реализации, обычно _authorizeUpgrade.
2. **Процесс обновления**:
- В UUPS обновление происходит путем замены адреса реализации, а сама логика обновлений определяется в реализации (например, через функцию authorizeUpgrade).
- Прокси просто делегирует вызовы на текущую реализацию.
3. **Преимущества**:
- Экономия на газе, так как прокси не содержит сложной логики.
- Логика обновлений находится в самой реализации, что делает систему более гибкой.
4. **Недостатки**:
- Необходимость правильно реализовать функцию _authorizeUpgrade для контроля доступа к обновлениям.
- Может быть сложнее для менее опытных разработчиков, так как требуется корректно настроить безопасность.
 
#### Beacon Proxy
1. **Механизм**: Beacon Proxy использует специальный контракт, называемый Beacon, который хранит адрес реализации. Прокси всегда делегирует вызовы на реализацию, указавшуюся в Beacon.
2. **Процесс обновления**:
- Вместо того, чтобы каждый прокси-контракт обновлять отдельно, все прокси могут делегировать вызовы на одну реализацию, которая определяется в Beacon.
- Когда адрес реализации в Beacon меняется, все связанные с ним прокси получают новую реализацию автоматически.
3. **Преимущества**:
- Удобно для управления множественными прокси. Если у вас есть несколько прокси, которые должны использовать одну и ту же реализацию, вы можете обновить её централизованно через Beacon.
- Уменьшение затрат на газ, так как обновление касается только Beacon, а не каждого отдельного прокси.
4. **Недостатки**:
- Немного более сложная структура, поскольку требуется наличие дополнительного контракта Beacon.
- Меньше гибкости для уникальных обновлений каждого прокси, так как все прокси должны использовать одну и ту же реализацию, определенную в Beacon.

### где находятся memory, calldata, storage
- memory - оперативная память EVM
- calldata доступна только во время выполнения транзакции. После завершения транзакции она удаляется из оперативной памяти EVM (узла), но остается записанной в блокчейне как часть транзакции в поле data.
- storage - хранится в БД узла (например, LevelDB для geth), данные являются частью блокчейна и сохраняются там навсегда.

### tx.origin, msg.sender

`tx.origin` - тот, кто первый инициировал транзакцую, во всей цепочке вызовов неизменен.\

`msg.sender` - тот, кто инициировал текущую транзакцию.

```solidity
// 0xAAA
contract A {
  function fun() {
    // tx.origin = 0xABC
    // msg.sender = 0xBBB
  }
}

// 0xBBB
contract B {
  A a;

  function callA() external {
    a.fun(); 
  }
}

// account 0xABC calls B.callA()
```

###  Чтобы контракт мог принимать деньги, нужно, чтобы в нем была объявлена функция receive (название может быть другое, в теле можно ничего не указывать):

```solidity
receive() external payable { }
```

###  Отправить деньги из контракта на адрес можно так:

```solidity
function withdraw() public {
  address payable recepient = payable(msg.sender);
  (bool success, ) = recepient.call{value: amount}("");

  // в случае нехватки эфира на контракте транзакция откатится назад, то есть она выполняется как атомарная операция.
  require(success);
}
```

###  Когда следует использовать public, а когда external?

public следует использовать только в том случае, если есть необходимость вызова функции изнутри контракта. external необходимо использовать, если предполагается вызов функции только снаружи контракта. Причина по которой external дешевле - использование calldata, из которой можно сразу же и читать, не копируя аргументы функции в memory, что является затратным действием.

###  За readable funcs (view, pure) платить не нужно, так как получить данные из контракта можно на локальной машине. При таких вызовах происходит так называемый CALL, и не transaction.

###  Есть две особенные функции receive, fallback

Если кто-то попробует отправить деньги на контракт напрямую через метод transfer, а не вызвать payable функцию, то в этом случае вызовется функция:

```solidity
receive() external payable { }
```

Если же такой функции нет, то деньги вернутся назад.

Если кто-то попробует вызвать функцию, которой нет в контракте, то вызовется fallback функция (может быть payable, если хотим принимать деньги):

```solidity
fallback() external {
  // здесь можно вернуть ошибку
}
```

###  По умолчанию у state variables модификатор видимости: `internal` - доступны изнутри и могут наследоваться.

###  Единицы измерения:
   - `1 ether` = `10 ** 18 wei`
   - `1 gwei` = `10 ** 9 wei`

   - За каждую транзакцию нужно платить, оценивается в gas. Например, `1 gas = 15 gwei`. Цена газа изменяется в зависимости от загруженности сети.

###  `call / send / transfer`:
   - `call` - низкоуровневый вызов, кроме денег можно отправлять еще и msg.data. Также можно указать лимит по газу, если receive функция контракта, куда мы отправляем деньги, очень дорогая(много действий): payable(to).call{value: amount, gasLimit: limit}("some data");
   - `transfer`, просто отправка денег, но установлен лимит по газу: 2300, порождает ошибку
   - `send`, просто отправка денег, но установлен лимит по газу: 2300, не порождает ошибку, возвращает bool

###  `gas price`, `gas limit`.
- `gas price` - текущая цена газа, выражается в gwei и зависит от загруженности сети. Например, если gas price в данный момент - 5 `gwei`, то за выполнение одного юнита пользователь заплатит `5 * 10^(-9) ETH`.
- `gas limit` - максимальное количество газа, которое пользователь готов потратить на выполнение транзакции. Например, если пользователь поставил `gas limit` = 21000, то он потратит `gas price` * `gas limit` = `5 gwei * 21000`

Допустим пользователь хочет выполнить функцию из смарт контракта и ставит gas-limit = 150'000. Есть два сценария:
1. Газа достаточно, и контракт завершён успешно: если контракт использовал только 80'000 газа, вы заплатите за 80,000 газа, а остаток вернётся.
2. Газа не хватает: если операция требует 150'000 газа, но вы указали Gas Limit = 100'000, транзакция остановится с ошибкой `out-of-gas`, и вы **потеряете уже израсходованный газ**.\



### Сценарии в EIP-1559 (Ethereum 2.0):
После внедрения EIP-1559, структура цены газа изменилась:
1. Base Fee (Базовая комиссия):
- Устанавливается протоколом Ethereum в зависимости от загрузки сети.
- Сжигается и не выплачивается валидатору.
2. Priority Fee (Чаевые):
- Пользователь задаёт вручную как мотивацию валидатору.
- Чем выше чаевые, тем быстрее транзакция обрабатывается.

> Итоговая стоимость для пользователя:
> (Base Fee + Priority Fee) x Gas Used
