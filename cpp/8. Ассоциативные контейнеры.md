# 8. Ассоциативные контейнеры

## Ассоциативные контейнеры

Ассоциативные контейнеры сопоставляют ключам некоторые значения.

Есть:

`map, set` - на сбалансированных деревьях поиска(rb tree).
`multimap, multiset` - на сбалансированных деревьях поиска(rb tree).

`unordered_map, unordered_set` - на хеш-таблицах.
`unordered_multimap, unordered_multiset` - на хеш-таблицах.

## std::map
```cpp
#include <map>

std::map<std::string, int> years = 
{
  {"Moscow", 1147}, 
  {"Rome", -753}, 
  {"London", 47},
}; 

for (const auto& [city, year] : years) { 
  std::cout << city << ": " << year << "\n"; 
}
```

При итерации range-based-for возвращается `std::pair`, можно распаковать(structured binding), прикрепив ссылки к `first`, `second`.

Так как реализованы с помощью rb tree, то итерирование происходит в порядке возрастания ключей. Но для того, чтобы использовать определенный тип как ключ, для него должен быть переопределены операторы сравнения.

Операции вставки, поиска, удаления происходят за O(logn).
```cpp
data[key] = value; // вставка элементы.

data.insert({key, value}); //вставка, если существует, то ничего не изменится.

data.insert_or_assign(key, value); // перезапишет значение, если существует такой ключ.

data.erase(key); // если ключа нет, то ничего не произойдет.
```

В случае, если при data[key] такого ключа нет, то в map вставится значение по умолчанию(например для int 0).

Поиск по ключу: 
```cpp
it = data.find(key) // вернет итератор на пару, если такая запись есть, иначе data.end().

data[key] > 0 - если ключа нет, то вставится {key, 0}
data.at(key) - если ключа нет, то исключение.
```

### Сортировка map 

Отсортировать мапу по значениям(value) нельзя. Но можно создать вектор пар и отсортировать его:
```cpp
std::vector<std::pair<std::string, int>> v(m.begin(), m.end());
std::sort(v.begin(), v.end(), [](const auto& a, const auto& b) {
	return a.second > b.second;
});
```

## std::unordered_map

Реализован на основе хеш-таблицы. Для того, чтобы тип данных мог быть ключом, для него должна быть определена хеш-функция. По ее результату вычисляется номер бакета, куда должно попасть новое значение.

Коллизии разрешаются методом цепочек. 

Если хеш функция достаточно равномерна и в хеш таблице достаточно много бакетов, то в среднем поиск/удаление/вставка происходит за O(1).

У контейнера unordered_map есть функция max_load_factor, которая задаёт максимально допустимое соотношение между числом элементов и количеством корзин. По умолчанию эта величина равна единице, так что unordered_map пытается в среднем вообще избежать коллизий. Но это не означает отсутствия коллизий в отдельных корзинах.

Если при вставке очередного элемента среднее число элементов в корзинах превышает этот порог, число корзин автоматически увеличивается и происходит рехеширование. Чем-то это напоминает реаллокацию у вектора.

Если нам заранее известно финальное количество ключей, то можно вызвать заранее функцию reserve и избежать лишних рехеширований при вставках. Тем самым можно отыграть дополнительное время.


## std::set, std::unordered_set

`std::set<type>` реализован на rbtree - хранит уникальные значения определенного типа <type>.

`std::set<type>` реализован на rbtree - хранит уникальные значения определенного типа <type>.

```cpp
std::set<int> s;
std::unordered_set <int> us;

bool sc = s.contains(1);
bool usc = us.contains(2);
```
Вставка:
```cpp
auto p = s.insert(1); // возвращает пару (it, search_reslult).
```

## std::multimap, std::unordered_multimap, std::multiset, std::unordered_multiset

Один и тот же элемент можно встретить несколько раз. Применять multimap имеет смысл там, где повторы ключей сравнительно редки.

У map, set итераторы можно сдвигать вперед и назад, и они не инвалидируются, как и ссылки и указатели.
У unordered можно сдвигать только вперед, так как коллизии разрешаются с помощью forward_list, итераторы могут инвалидироваться при рехешировании, ссылки и указатели нет.

**Рехеширование** - процесс изменения значения хеш-таблицы и перераспределение ее элементов в памяти. 

Есть следующие стратегии рехеширования:
Удвоение размера: При этой стратегии новая таблица имеет удвоенный размер по сравнению с текущей. Это позволяет более равномерно распределить элементы и обеспечить эффективную работу таблицы. Однако это требует дополнительной памяти. 
Уменьшение размера: В некоторых случаях, если таблица стала слишком маленькой после множественных удалений, может потребоваться уменьшить её размер, чтобы сэкономить память. 
Двойное хеширование: Это метод рехеширования, при котором элементы перераспределяются в таблицу нового размера с использованием другой хеш-функции. Это может помочь избежать кластеризации элементов, если первая хеш-функция вызывает коллизии.
