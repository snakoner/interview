# 15. Умные указатели

## Умные указатели

Для “обычных” указателей при выделении памяти нужно обязательно эту память очищать, иначе будет утечка памяти - неконтролируемое уменьшение оперативной памяти компьютера.

Умные указатели являются классом оберткой над обычными указателями, где перегружены операторы -> и *. Когда умный указатель выходит из области видимости, срабатывает его деструктор и происходит очистка памяти.

Виды умных указателей:

`std::unique_ptr` — умный указатель, владеющий динамически выделенным ресурсом; 
`std::shared_ptr` — умный указатель, владеющий разделяемым динамически выделенным ресурсом. Несколько `std::shared_ptr` могут владеть одним и тем же ресурсом, и внутренний счетчик ведет их учет; 
`std::weak_ptr` — подобен `std::shared_ptr`, но не увеличивает счетчик.

### std::unique_ptr


`std::unique_ptr` владеет объектом, на который он указывает, и никакие другие умные указатели не могут на него указывать(технически это происходит потому, что у std::unique_ptr нет конструктора копирования).

#### Использование:

```cpp
std::unique_ptr<int[]>  p2(new int[50]);
std::unique_ptr<int[]> ptr = std::make_unique<int[]>(50);
```

#### Свойства:

1. Когда `std::unique_ptr` выходит из области видимости, утечки памяти не происходит, потому что в своем деструкторе умный указатель вызывает `delete` для объекта на который ссылается, высвобождая тем самым память.
2. Пример:
```cpp
int main() {
   auto ptr = std::make_unique<int[]>(100);
   ptr = std::make_unique<int[]>(200);
}
```

В данном случае утечки памяти не произойдет, потому как в операторе присваивания произойдет `delete` памяти, на которую ссылается ptr в первом случае.

4. Кроме того, в случае, если после создания std::unique_ptr(память была выделена через new или make_unique) произошло исключение, то из-за механизма свертки стека будет вызван десткруктор и память будет освобождена.
5. Лучше всегда использовать std::make_unique вместо (new[]):
- с умными указателями явно не принято использовать new/delete.
- это позволяет не писать имя класса дважды: вместо `std::unique_ptr<char[]> ptr(new char[20]);` получаем `auto ptr = std::make_shared<char[]>(20);`
- использование make_unique решает проблему неопределенности выполнения операций:

```cpp
void func(std::unique_ptr<A> a, std::unique_ptr<B> b) {}
int main() {
    func(std::unique_ptr<A>(new A()), std::unique_ptr<B>(new B())); // здесь порядок может быть такой: new A(), new B(), std::unique_ptr<A>(), std::unique_ptr<B>().
}
```

В данном случае, если произойдет исключение например при new B(), то выделеная при new A() память не освободится, так как обьекты std::unique_ptr еще не были созданы


### std::shared_ptr

`std::shared_ptr` в отличие от `std::unique_ptr` допускает множественные ссылки. Специальный внутренний счетчик уменьшается каждый раз, когда `std::shared_ptr`, указывающий на тот же ресурс, выходит из области видимости. Эта техника называется подсчетом ссылок. Когда последняя из них будет уничтожена, счетчик станет равным нулю, и данные будут высвобождены.

Использование:

```cpp
std::shared_ptr<int>    p1(new int);
std::shared_ptr<int>    p1 = std::make_shared<int>();
```

В shared_ptr нужно быть осторожным с круговыми ссылками:

```cpp
struct Player
{
 std::shared_ptr<Player> companion;
 ~Player() { std::cout << "~Player\n"; }
};

int main()
{
 std::shared_ptr<Player> jasmine = std::make_shared<Player>();
 std::shared_ptr<Player> albert  = std::make_shared<Player>();


 jasmine->companion = albert; // (1)
 albert->companion  = jasmine; // (2)
}
```


В итоге после выхода из области видимости(функция main) счетчик ссылок jasmine равен 1, так как на нее указывает albert->companion. Аналогично в albert, на него указывает jasmin->companion. Поэтому деструкторы не будут вызваны - утечка памяти.
