# 6. Нижняя половина обработчика прерывания

> softirq и tasklet выполняются в контексте прерывания(при возврате из аппаратного прерывания) и в контекте процесса(поток ядра ksoftirqd), workqueue всегда в контексте процесса.

Обработчики прерываний должны выполняться быстро, при этом не могут входить в состояние ожидания. Поэтому вся остальная работа(менее критичная ко времени выполнения) перекладывается на нижнюю половину(bottom half) обработчика прерывания. 

Нужно планировать bottom half сразу же после проделывания всей работы в top half. Сама же нижняя половина запустится, когда процессор будет не так занят, но обычно это происходит сразу после выхода из обработчика.

Существует три механизма организации обработчиков нижней половины: отложенные прерывания, тасклеты, очереди отложенных действий.

## Отложенные прерывания(softirq)

Определяются статически во время компиляции. В отличие от тасклетов, нельзя динамически зарегистрировать или удалить отложенное прерывание.

Каждое softirq описывается структурой:
```cpp
struct softirq_action {
    void (*action)(struct softirq_action *);
};
```

Глобальный массив, хранящий 32 таких softirq:
```cpp
static struct softirq_action softirq_vec[NR_SOFTIRQS];
```

NR_SOFTIRQS - максимальное значение 32, нельзя изменить динамически (возможно есть ограничение и на изменение дефайна).

Сам обрабочик определяется c такой сигнатурой:

```cpp
void softirq_handler(struct softirq_action *)
```

Тонкости работы:
1. Обработчик одного отложенного прерывания никогда не может вытеснить другой такой же обработчик.
2. Только аппаратное прерывание может вытеснить обработчик отложенного прерывания.
3. На другом процессоре одновременно с обработчиком отложенного прерывания может выполняться другой
(и даже этот же) обработчик отложенного прерывания.** Из-за этого нужно блокировать shared данные! Но чтобы достичь большей производительности для параллельного выполнения двух одинаковых обработчиков, лучше использовать данные, уникальные для каждого процессора. **
4. Обработчик не может переходить в состояние ожидания.
5. Аппаратные прерывания не запрещаются.

Главная причина использования softirq - маштабируемость (возможность параллельного выполнения одного softirq на разных ядрах).

Запуск отложенные обработчиков прерывания выполняется в следующих случаях:
1. После возврата из аппаратного прерывания (неявный вызов do_softirq)
2. В контексте потока `ksoftirqd` (неявный вызов do_softirq).
3. Явный вызов `do_softirq()` - проходит по вектору `softirq_vec` и вызывает все ожидающие выполнения по порядку.

Задать номера отложенных прерываний можно через `<linux/interrupt.h>`. Прерывания с меньшим номеров выполнятся раньше прерываний с большим номером.
В данном файле с помощью enum уже зарезервинованы номера для отложенных прерываний:
```cpp
HI_SOFTIRQ             0 высокоприоритетные тасклеты
TIMER_SOFTIRQ         1 таймеры
NET_TX_SOFTIRQ         2    отправка сетевых пакетов
...
```
Регистрация softirq:
```cpp
open_softirq(NET_TX_SOFTIRQ, net_tx_action);        // (enum number, softirq_action)
```

Маркировка softirq (по сути запуск на планирование):
```cpp
raise_softirq(NET_TX_SOFTIRQ); // теперь обработчик будет вызван при вызове do_softirq().
```

Перед тем, как сгенерировать softirq, `raise_softirq()` запрещает прерывания, а потом после запуска разрешает их.

## Tasklet

Реализованы на основе `softirq`. Имеют более простой интерфейс и упрощенные правила блокировок. Лучше всегда использовать их.

Тасклеты представлены двумя типами отложенных прерываний: `HI_SOFTIRQ` и `TASKLET_SOFTIRQ`. `HI_SOFTIRQ` запускаются всегда раньше `TASKLET_SOFTIRQ`.

Структура, описывающая тасклет:

```cpp
struct tasklet_struct {
    struct tasklet_struct *next; /* Указатель на следующий тасклет в списке */
    unsigned long state; /* Состояние тасклета: TASKLET_STATE_SCHED(запланирован) или TASKLET_STATE_RUN(выполняется сейчас) */
    atomic_t count; /* Счетчик ссылок. 0 - может запуститься, если запланирован. > 0 - не может быть запущен */
    void (*func)(unsigned long); /* Функция-обработчик тасклета */
    unsigned long data; /* Аргумент функции-обработчика тасклета */
};
```

Все тасклеты хранятся в структурах:
`tasklet_vec` (для обычных тасклетов) и `tasklet_hi_vec`(для высокоприоритетных тасклетов) - связный список. Уникальны для каждого процессора.

Планирование за работу:
```cpp
tasklet_schedule(tasklet_struct_);
или
tasklet_hi_schedule(tasklet_struct_);
```

Тонкости работы:
1. Вытеснить тасклет может только аппаратное прерывание.
2. Один тасклет может выполняться одновременно только на одном процессоре.
3. Разные тасклеты могут выполняться одновременно на разных процессорах.
4. Не может переходить в состояние ожидания.
   
### Обьявление тасклета:
```cpp
DECLARE_TASKLET(my_tasklet, my_tasklet_handler, dev); // статически
tasklet_init(t, tasklet_handler, dev); // динамически
```

Прототип для handler:

```cpp
void tasklet_handler(unsigned long data)
```

Планирование на выполнение:

```cpp
tasklet_schedule(&my_tasklet);
```

Если тасклет уже запланирован, но не выполняется, то он будет запланирован всего один раз. Если уже выполняется, то будет запущен еще раз.

Отключение тасклета:
```cpp
tasklet_disable(&my_tasklet); /* тасклет теперь отключен */
```

Тасклет будет всегда запускаться на том же процессоре, который запланировал его на выполнение. Это позволяет надеяться на лучшее использование кеш-памяти процессора. (Это можно изменить через `procfs`).

### ksoftirqd 

`do_softirq()` вызывается при выходе из hw прерывания. Но что если прерывание давно не происходило. Для этого есть потоки ядра.
Для каждого процессора существует свой поток ядра. Каждому потоку присвоено имя в виде `ksoftirqd/n,` где n — номер процессора. Работает на минимальном приоритете(nice = 19). 
Он вызывает функцию `do_softirq().` 

Если какое-то из отложенных прерываний активизирует само себя, то его обработчик не будет запущен до того момента, пока
ядро в следующий раз снова не приступит к их обработке.

## Очереди отложенных действий(work queue)

Данный тип нижних половин обработчиков всегда выполняется в контексте процесса и, как следствие, пользуется всеми преимуществами контекста процесса. Главное из них
состоит в том, что этим процессом управляет системный планировщик, **поэтому выполняющийся код может переходить в состояние ожидания**.

Отложенные действия выполняются в рабочих потоках ядра (work thread). В ядре предусмотрен специальный стандартный рабочий поток, выполняющий нужную работу. Поэтому в самом общем случае очереди отложенных действий — это простой интерфейс пользователя для откладывания работы, которая будет стандартным потоком ядра. 
Стандартный поток ядра называется `events/n`, где n-номер процессорного ядра. В однопроцессорной системе есть только один стандартный поток `events/0`.

Но ничто не запрещает коду ядра **создавать собственные рабочие потоки**. Это может понадобиться, если в рабочем потоке выполняется большое количество вычислительных операций. Для операций, интенсивно использующих центральный процессор или критичных ко времени выполнения, также имеет смысл создавать отдельные рабочие потоки. В результате будет уменьшена нагрузка на стандартные рабочие потоки и устранена проблема нехватки ресурсов для выполнения остальных отложенных действий.

Рабочие потоки представляются с помощью структуры `workqueue_struct`:

```cpp
struct workqueue_struct {
    struct cpu_workqueue_struct cpu_wq[NR_CPUS];
    struct list_head list;
    const char *name;
    int singlethread;
    int freezeable;
    int rt;
};
```

Все рабочие потоки реализованы как обычные потоки ядра, которые выполняют функцию `worker_thread()`. После начальной инициализации эта функция входит в бесконечный цикл и переходит в состояние ожидания. Когда какая-либо работа ставится в очередь, поток активизируется и выполняет ее. Когда в очереди не остается работы, которую нужно выполнить, поток снова переходит в состояние ожидания.

Каждое действие представлено с помощью структуры `work_struct`:

```cpp
struct work_struct {
    atomic_long_t data;
    struct list_head entry;
    work_func_t func;
};
```

Эти структуры объединены в связанный список, по одному списку на каждый тип очереди для каждого процессора. Например, для каждого процессора существует список отложенных действий, которые выполняются стандартными рабочими потоками. При активизации рабочий поток начинает выполнять все действия, которые находятся в его списке.
После завершения работы он удаляет соответствующие структуры work_struct из связанного списка. Когда список становится пустым, поток переходит в состояние ожидания.

В функции work_thread() в бесконечном цикле выполняются перечисленные ниже действия:
1. Поток изменяет свое состояние на состояние ожидания (флаг состояния задачи устанавливается в значение `TASK_INTERRUPTIBLE`) и добавляет себя в очередь ожидания.
2. Если связанный список действий пуст, то поток вызывает функцию `schedule()` и переходит в состояние ожидания.
3. Если список не пустой, то поток не переходит в состояние ожидания. Он устанавливает свое состояние в значение `TASK_RUNNING` и удаляет себя из очереди ожидания.
4. Если список не пустой, то вызывается функция `run_workqueue()` для выполнения отложенных действий. Тогда поток перебирает все запланированные действия в `worklist` и выполняет их по порядку. Выполненное действие удаляется из списка действий `worklist`.

Создание отложенного действия:
```cpp
DECLARE_WORK(name, void (*func)(void *), void *data); // статически
INIT_WORK(struct work_struct *work, void (*func)(void *), void *data); // динамически
```

Прототип обработчика отложенного действия имеет вид:
```cpp
void work_handler(void *data);
```

Обратите внимание: хотя функция-обработчик и выполняется в контексте процесса, из рабочего потока нельзя обращаться к содержимому памяти пространства пользователя.
Все дело в том, что адресное пространство пользователя не отображается в адресное пространство потока ядра. Ядро может обращаться к пользовательской памяти только
тогда, когда оно выполняется от имени пользовательского процесса, как, например, в случае вызова системной функции. Только в этом случае адресное пространство пользователя отображается в память ядра.

Для постановки действия в очередь:
```cpp
schedule_work(&work);
```

Данное отложенное действие будет запланировано на выполнение немедленно и выполнено, как только рабочий поток events, запущенный на текущем процессоре, выйдет из состояния ожидания.

Если необходимо создать новую очередь отложенных действий(в этом случае создастся и рабочий поток свой для каждого процессора):
```
struct workqueue_struct *create_workqueue(const char *name);
```

В отличие от стандратных потоков ядра, действие планируются вот так:
```cpp
int queue_work(struct workqueue_struct *wq, struct work_struct *work); // планирование в очереди(в потоке) wq
```
