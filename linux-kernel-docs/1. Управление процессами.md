# 1. Управление процессами

## Понятие процесса

**Процесс** - это объектный код, хранящийся на каком-то носителе, _который находится в состоянии выполнения_, включающий в себя кроме кода:
1. Набор открытых файлов
1. Сигналы, ожидающие обработки
1. Состояние процессора (регистровый файл...)
1. Адресное пространство процесса(text, bss, data, mmap)
2. Стек процесса
1. Один или несколько потоков

В Linux, существует три типа процессов:

1. пользовательские
2. процессы-демоны
3. потоки ядра

**Пользовательские Linux процессы** — работают от имени обычной учетной записи пользователя и выполняются в **пространстве пользователя**. Если процесс не запущен таким образом, который дает процессу дополнительные разрешения, то пользовательский процесс не имеет доступа к файлам в системе, к которым не имеет доступа сам пользователь запустивший процесс.

**Процессы-демоны** — это фоновый процесс, который не привязан к терминалу, в котором был запущен. Демоны обычно запускаются во время загрузки системы. Типичные задачи демонов: серверы сетевых протоколов (HTTP, FTP, электронная почта и др.), управление оборудованием, поддержка очередей печати, управление выполнением заданий по расписанию(cron, который просыпается раз в минуту) и т. д. В техническом смысле демоном считается процесс, который не имеет управляющего терминала. Чаще всего (но не обязательно) предком демона является `init` — корневой процесс UNIX.

**Процессы(потоки) ядра** — выполняются **только в пространстве ядра**. Они похожи на процессы-демоны. Основное отличие состоит в том, что процессы ядра имеют полный доступ к структурам ядра. Процессы ядра не так гибки, как процессы-демоны. Вы можете изменить поведение процесса-демона, изменив конфигурационные файлы и перезагрузив службу, но для изменения потоков ядра может потребоваться перекомпиляция ядра.



**Поток процесса** - объект, выполняющий определенные действия внутри процесса. В каждом потоке содержится уникальные счетчик команд(program counter), стек процесса, набор регистров процессора.
Поток в операционной системе - специальный вид процесса, который совместно с другими потоками процесса разделяет его ресурсы.

> _Планировщик управляет не процессами, а потоками._

> Важно: поток харакетируется:
> 1. идентификатор потока
> 2. program counter
> 3. собственный стек
> 4. состояние регистров

## Контекст процеса

**Контекст процесса** - это минимальный набор данных, используемых задачей, который должен быть сохранен, чтобы позволить прервать задачу и позже продолжить ее с той же точки.

Каждому процессу соответствует контекст, в котором он выполняется. Этот контекст включает содержимое пользовательского адресного пространства - пользовательский контекст (т.е. содержимое сегментов программного кода, данных, стека, разделяемых сегментов и сегментов файлов, отображаемых в виртуальную память), содержимое аппаратных регистров - регистровый контекст (таких, как регистр счетчика команд, регистр состояния процессора, регистр указателя стека и регистров общего назначения), а также структуры данных ядра (контекст системного уровня), связанные с этим процессом.

Аналогичным образом, есть контект прерывания и контекст ядра.

## Как создается процесс?

Процесс создается с помощью системной функции `fork()`. Создается почти полная копия уже существующего процесса. Созданный процесс - **дочерний**, процесс, создавший его, называется **родительским**.
Не копируются следующие ресурсы и данные:
1. `PID` - новый pid для порожденного процесса.
2. `PPID` - pid родительского процесса также меняется.
3. Сигналы, ожидающие обработки.
4. Статистика использования ресурсов - обнуляется.

Завершение процесса - вызов системной функции `exit()`, которая также освобождает все занятые ресурсы процесса. После завершения процесса, он переводится в состояние **zombie**, которое используется для возможности получить код возврата.

> fork() возвращает 0 для дочернего процесса, реальный pid нового процесса для родительского процесса.

### Беспризорный процесс.

Если родительский процесс завершился раньше, чем дочерний, то дочерний остается без родителя и навсегда может остаться в состоянии zombie: в этом случае родительским может стать либо `init`, либо другой поток из потоков группы завершившегося процесса.

## Завершение процесса

Процесс может завершиться в следующий случаях:
1. Явный вызов процессом exit()
2. Получение сигнала
3. Exception, который процесс не может обработать.

Внутри exit - `do_exit()`: после завершения этой функции процесс находится в состояние `zombie`, но `task_struct` все еще существует - это позволяет родительскому процессу получить информацию о его завершении. Как только родительский процесс получил эту информацию или сообщил ядру, что эта информация ему больше не нужна, происходит освобождение `task_struct`.
### Функци wait

Вызов `wait()` приостанавливает выполнение родительского процесса до того момента, пока один из дочерних процессов не завершится. При этом wait возвращает pid завершившегося процесса.

### Copy on write
Так как порожденный процесс может сразу же запустить другой исполняемый файл, то полное копирование адресного пространства является нерациональным. Вместо этого, при выполнении fork() используется механизм `копирование при записи`. При этом данные помечаются определенным образом.
Если оба процесса используют адресное пространство только на чтение, то ничего не происходит. Как только какой-либо из процессов делает запись в данные, то для порожденного процесса создается копия страницы данных.
Издержки, которые возникают при таком подходе: выделение памяти для дескриптора задач (ускоряется при использовании SLAB) и копирование таблицы страниц.

```cpp
vfork() - то же самое, что и fork, но не копирует таблицы страниц родительского процесса.
```

Стек создания процесса:
`fork() -> {SYSCALL}clone() -> do_fork() = copy_process() + запускает новый процесс на выполнение.`

> Ядро намеренно запускает дочерний процесс раньше родительского, так как иначе бы родительский процесс мог бы записать что-то в свои данные, следовательно из-за COW пришлось бы делать копию для дочернего процесса. Но если дочерний процесс сразу же выполняет `exec()`, то такое копирование - это потеря времени, так как данные все равно перетрутся.

## task_struct

Список всех процессов хранится в ядре с помощью двусвязного циклического списка, состоящим из структур `task_struct`, который называется `task_list`. 
Каждый процесс описывается с помощью структуры(дескриптор процесса), которая полностью описывает его состояние:
```cpp
struct task_struct {
  unsigned long state; // состояние процесса
  int prio;          // приоритет
  struct task_struct *parent;  // родительский процесс
  struct list_head tasks; // для связывания в двусвязный список
  pid_t pid;          // id процесса
  struct mm_struct		*mm;  // указатель на адресное пространство
  void* stack;  // стек процесса
}
```

## thread_info

Раньше не во всех аппаратных платформах было достаточно регистров для хранения дополнительного указателя на дескриптор текущей задачи, поэтому чтобы иметь быстрый доступ в `task_struct`, было принято ввести новую структуру `thread_info`, которая всегда хранится в вершине стека **ядра** процесса:

```cpp
struct thread_info {
  struct task_struct *task;      // указатель на дескриптор задачи
  struct exec_domain *exec_domain;
  __u32 flags;
  __u32 status;
  __u32 cpu;              // на каком CPU сейчас выполняется
  int preempt_count;
  mm_segment_t addr_limit;
  struct restart_block restart_block;
  ...
}
```

Получить дескриптор процесса можно двумя способами:
```cpp
current_thread_info()->task
```
или
```cpp
current()
```

В некоторых аппаратных системах адрес `task_struct` хранится в одном из регистров процессора.

## Идентификация процесса

Каждый процесс имеет в системе специальный идентификатор `pid` типа `pid_t`(int). Для обратной совместимости со старыми версиями Linux это значение не превышает 32K, но при желании его можно увеличить с помощью изменеия дефайна. Максимальное значение определяется максимальное число процессов, которые могут существовать в ядре одновременно.

## Состояние процесса

Описывается полем `state` в `task_struct`. Может принимать следующие значения:
1. `TASK_RUNNING` - процесс либо выполняется, либо готов к выполнению(находится в очереди `runqueue`).
2. `TASK_INTERRUPTIBLE` - процесс приостановлен (sleeping), т.е. заморожен до наступления некоторого события. При наступлении данного события ядро переводит процесс в состояние TASK_RUNNING.  Процесс можно разморозить по сигналу или по истечении таймера.
3. `TASK_UNINTERRUPTIBLE` - процесс приостановлен (sleeping), это состояние аналогично TASK_INTERRUPTIBLE, за исключением того, что процесс нельзя разморозить и перевести в исполняемое состояние с помощью специального сигнала.
4. `TASK_TRACED` - выполняется трассировка процесса другим процессом
5. `TASK_STOPPED` - выполнение процесса остановлено. Задача не выполняется и не имеет права выполняться. Такое может случиться, если задача получает какой-либо из сигналов (SIGSTOP, SIGTSTP, SIGTTIN или SIGTTOU)
6. `TASK_ZOMBIE` - процесс завершен

Перевести задачу `task` в состояние `state` можно так:
```cpp
set_task_state(task, state);
```

Все процессы(за исключением процессов(потоков) ядра), основную часть времени выполняются в userspace. Перейти в пространоство ядра можно только с помощью системных вызовов или при возникновении exception.

## Какой процесс самый первый?

Все процессы являются потомками процесса `init`, значение идентификатора PID для которого равно 1. Ядро запускает процесс `init` на последнем шаге процедуры начальной загрузки системы. Процесс `init`, в свою очередь, читает системные файлы сценариев начальной загрузки (`initscripts`) и запускает другие программы, в результате чего процедура начальной загрузки завершается. Структура для `init` выделяется статически.

Каждый процесс может иметь только одного родителя: `task->parent` и одного или несколько потомков: `task->children`. Таким образом, можно имея один процесс прийти к любому другому.

## Потоки
С точки зрения Linux поток - процесс, который использует ресурсы процесса совместно с другими потоками.

Создаются потоки так же, как и процессы, но в аргумент функции `clone()` передаются специальные флаги:
```cpp
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND, 0);
```

Результат выполнения функции `clone` с этими флагами будет таким же, что и вызов `fork`, за исключением разделяемых ресурсов.

Основные флаги:
1. `CLONE_FILES` - совместное использование открытых файлов
2. `CLONE_FS` - совместное использование информации о файловой системе.
3. `CLONE_VM` - общее адресное пространство.
4. `CLONE_SIGHAND` - общие обработчики сигналов.

## Потоки ядра
**Потоки ядра** - процессы, которые выполняются исключительно в kernel-space. Еще одно отличие - отсутствие собственного адресного пространства(указатель `mm = NULL`, таким образом поток ядра имеет доступ ко всему коду и структурам данных ядра).

Потоки ядра создаются во время начальной загрузки системы от потока `kthreadd`. 

Чтобы создать поток ядра:
```cpp
kthread_create()
```

После создания поток не будет запущен. Для этого нужно вызвать функцию:
```cpp
wake_up_process() 
```

Так же есть возможность сразу создать и запустить поток:
```cpp
kthread_run()
```

Поток ядра будет выполняться до тех пор, пока в потоке не будет явно вызвана функция `do_exit()`, либо в другой части ядра не будет вызвана `kthread_stop()`.

Поток `ksoftirqd` ответственнен за вызов нижней половины обработчиков прерывания.
