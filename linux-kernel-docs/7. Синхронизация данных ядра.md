# SMP-системы
Симметричная мультипроцессорная система (SMP, Symmetric Multiprocessor) — это вычислительная система, обладающая следующими характеристиками:
1. имеется два или более процессоров сопоставимой производительности
2. процессоры совместно используют основную память и работают в едином виртуальном и физическом адресном пространстве
3. все процессоры связаны между собой посредством шины или по иной схеме, так что время доступа к памяти для любого из них одинаково
4. любой из процессоров может обслуживать внешние прерывания

В отличие от слабо связанных мультипроцессорных систем (кластеров), где в качестве физической единицы обмена информацией выступает сообщение или полный файл, в SMP допустимо взаимодействие на уровне отдельного элемента данных. Благодаря этому достигается высокий уровень связности между процессами.


Хотя технически SМР-системы симметричны, в их работе присутствует небольшой фактор перекоса, который вносит программное обеспечение. На время загрузки системы один из процессоров получает статус ведущего (master). Это не означает, что позже во время работы какие-то процессоры будут ведомыми, — все они в SMP-системе равноправны. Термин «ведущий» относится к тому процессору, который по умолчанию будет руководить первоначальной загрузкой вычислительной системы.

По сравнению с однопроцессорными схемами SMP-системы имеют преимущество по следующим показателям:
1. производительность: если процесс можно распараллелить, это дает выигрыш в производительности
2. готовность: отказ одного из компонентов не ведет к отказу системы
3. расширяемость: производительность системы может быть увеличена добавлением дополнительных процессоров
4. масштабируемость: варьируя число процессоров в системе, можно создать системы различной производительности и стоимости

# Общие сведения

В приложениях, использующих общую память (shared memory), разработчики должны позаботиться о том, чтобы совместно используемые ресурсы были защищены от конкурентного доступа. В этом смысле ядро Linux не является исключением. Совместно используемые ресурсы требуют защиты от конкурентного доступа в связи с тем, что несколько одновременно запущенных потоков команд могут одновременно изменять одни и те же данные. В результате один поток может затереть в памяти изменения, внесенные другим потоком, или обратиться к данным в тот момент, когда они находятся в несогласованном (т.е. противоречивом) состоянии. Конкурентный доступ к совместно используемым данным часто является причиной нестабильной работы системы, которую, как показывает опыт, впоследствии очень сложно обнаружить и исправить. В связи с этим важно при разработке кода сразу сделать все правильно.

## Критические участки

Критические участки(секции) - фрагменты кода, в которых выполняется доступ к совместно используемым данным и их изменение. Для предотвращения конкурентного доступа к ресурсам из критических участков программист должен обеспечить неделимое выполнение кода. Другими словами, выполнение критического участка кода не должно прерываться, как если бы весь
этот участок был одной неделимой машинной командой. В противном случае между потоками возникает race condition - при этом потоки как бы соревнуются за то, кто первым получит к нему
доступ.

### Пример

Рассмотри команду `i++`. Пусть есть два потока, одновременно выполнящих этот код. 

Это выражение можно перевести в команды процессора вычислительной машины следующим образом:
1. Загрузить текущее значение переменной `i` из памяти в регистр.
1. Прибавить единицу к значению, которое находится в регистре.
1. Записать новое значение переменной `i` обратно в память.

Ожидаемая поледовательность команд:

```c
Поток 1                       Поток 2
Загрузить i (7)               –
Увеличить i на 1 (7 -> 8)     –
Записать i (8)                –
–                             Загрузить i (8)
–                             Увеличить i на 1 (8 -> 9)
–                             Записать i (9)
```

Но может произойти следующее:

```c
Поток 1                       Поток 2
Загрузить i (7)               Загрузить i (7)
Увеличить i на 1 (7 -> 8)     –
–                             Увеличить i на 1 (7 -> 8)
Записать i (8)                –
–                             Записать i (8)
```

Таким образом, если i каким-то один из потоков будет читать до того, как другой поток запишет результат инкремента в память, то результат будет неверный.
Одним из способов предотвратить это - неделимая команда: она, не прерываясь читает, изменяет и пишет в память. Это гарантируется на физическом уровне при разработке процессора.

Но если критический участок кода не состоит лишь из одной команды, то здесь помогут **блокировки**.

## Общие способы синхронизации

Блокировки - механизм, предотвращающий доступ к ресурсу на то время, пока другой поток выполняет код в критическом участке.
Если в каком-то фрагменте кода требуется получить доступ к элементам очереди, то вначале нужно захватить соответствующую блокировку.

Рассмотрим последовательность действий при использовании блокировок:

```c
Поток 1                         Поток 2
Захват блокировки               Захват блокировки
Успешно: блокировка захвачена   Отказ: ожидаем освобождения...
Доступ к очереди                Ожидаем...
Освобождение блокировки         Ожидаем...
                                Успешно: блокировка захвачена
                                Доступ к очереди
                                Освобождение блокировки
```
Все блокировки реализованы на основе неделимых операций, которые гарантируют, что захват и освобождение данной блокировки не может прерваться.
С помощью всего одной машинной команды можно проверить, захвачен ли ключ, и, если нет, захватить его. Конкретная реализация этого процесса зависит от используемой аппаратной платформы. Однако практически во всех процессорах существует неделимая машинная команда типа
test-and-set (проверить и установить), которая позволяет проверить значение целочисленной переменной и присвоить ей указанное число, если ее значение равно нулю.

## Причины возникновения параллелизма

При работе в пространстве пользователя необходимость синхронизации возникает из-за того, что выполнение программы может быть принудительно прервано по воле планировщика. Поскольку в любой момент времени планировщик может вытеснить текущий процесс, выполняющийся на данном процессоре, и заменить его другим процессом, не исключено, что процесс может быть вытеснен по независящим от него причинам во время выполнения критического участка кода. Если новый, запланированный на выполнение процесс входит в тот же критический участок (скажем, если оба процесса — потоки одной программы, которые могут обращаться к общей памяти или записывать данные в общий файл), то может возникнуть конфликт из-за доступа к ресурсам. Аналогичная проблема может возникнуть при выполнении нескольких однопоточных программ, обращающихся к общему файлу, или даже в рамках одной программы, использующей сигналы, так как сигналы могут приходить асинхронно. Такой тип параллелизма, когда два события происходят не одновременно, а как бы накладываются друг на друга, вроде они происходят в один момент времени, называется **псевдопараллелизмом**.

Для однопоточной программы есть такие проблемы:
1. Если две однопоточные программы читают/пишут один и тот же файл.
2. Если в однопоточной программе приходит сигнал, а в обработчике сигнала обрабатываются те же данные.

Для однопроцессорной системы (если у процесса есть больше одного потока):
1. Есть два потока процесса, которые выполняются псевдопараллельно. Если включено вытеснение, то в любой момент первый поток может быть вытеснен вторым, тем самым может заново изменить данные, но изменения предыдущего потока еще не были записаны в память.

На машине с симметричной многопроцессорной обработкой два процесса могут действительно заходить в критические участки кода в один и тот же момент времени. Такой вид параллелизма называется истинным параллелизмом.

## Взаимоблокировки

**Deadlock** - все N потоков находятся в состоянии ожидания освобождения блокировки, когда в системе всего N потоков. Таким образом, никто из потоков не сможет освободить блокировку и как следствие все потоки будут в режиме ожидания бесконечно долго.

 Самый простой пример - **самоблокировка**(self deablock) - попытка потока захватить уже захваченную им же блокировку.

 Пример для двух потоков:

```c
Поток 1                           Поток 2
Захват блокировки A               Захват блокировки B
Попытка захвата блокировки B      Попытка захвата блокировки A
Ожидание блокировки B             Ожидание блокировки A
```

Нужно следить за тем, чтобы в несколько блокировок захватывались в одинаковом порядке, иначе:

```c
Поток 1                           Поток 2
Захват блокировки cat             Захват блокировки fox
Захват блокировки dog             Попытка захвата блокировки dog
Попытка захвата блокировки fox    Ожидание блокировки dog
Ожидание блокировки fox
```

# Примитивы синхронизации ядра

## Неделимые операции

`Неделимые операции` (atomic operations) представляют собой набор машинных команд, которые выполняются как одна цельная машинная команда, т.е.
не прерываясь.
В Linux есть неделимые целочисленные операции и неделимые битовые операции.

### Неделимые целочисленные операции

Предусмотрен тип `atomic_t`.

```cpp
typedef struct {
  volatile int counter;
} atomic_t;
```

и `atomic64_t`:

```cpp
typedef struct {
  volatile long counter;
} atomic64_t;
```

Пример функций:

```cpp
atomic_t u = ATOMIC_INIT(int i) // инициализация u значением i
int atomic_read(atomic_t *v) 
void atomic_set(atomic_t *v, int i)
void atomic_add(int i, atomic_t *v) 
void atomic_sub(int i, atomic_t *v) 
void atomic_inc(atomic_t *v) 
void atomic_dec(atomic_t *v) 
```

### Неделимые битовые операции

Кроме неделимых целочисленных операций, в ядре также предусмотрено семейство функций, позволяющих работать на уровне отдельных битов. Для таких операций нет отдельного типа данных, неделимость реализована в функциях:

```cpp
void set_bit(int nr, void *addr)
void clear_bit(int nr, void *addr)
void change_bit(int nr, void *addr)
int test_and_set_bit (int nr, void *addr)
int test_and_clear_bit(int nr, void *addr)
int test_and_change_bit(int nr, void *addr)
int test_bit(int nr, void *addr)
```

Также предусмотрены обычные битовые операции, они начинаются с __, например `__test_bit()`.

## spinlock

Важно
1. spinlock принадлежит процессору
2. если поток захватывает spinlock, то в функции spin_lock() выполняется запрет вытеснения на текущем процессоре: preempt_disable()[прерывания от таймера происходят, но задача не переключается на другую]. Таким образом поток будет выполняться пока:
    1. пока сам поток не отпустит блокировку. Таким образом захват блокировки в другом потоке невозможен, так как задача не будет вытеснена(не случится deadlock).
    2. пока не произойдет прерывание. Если прерывание использует ту же блокировку, то необходимо отключать прерывания перед захватом блокировки.
3. Пусть на другом процессоре будет выполняться поток, который так же попробует захватить блокировку: так как spinlock принадлежит другому процессору, то второй поток перейдет в busy loop и не случится deadlock.



Features:

1. Может быть захвачена не более чем в одном потоке команд.
2. При этом второй поток входит в цикл и начинает в нем постоянно проверять, не освободилась ли уже требуемая блокировка (busy loop).
3. Если блокировка свободна, поток может сразу же ее захватить и продолжить свое выполнение.  (атомарный test_and_set)
4. Спин-блокировки разумно использовать, если время ее удержания меньше чем два переключения контекста(как в случае с мьютексами).
5. Задача, ожидающая снятия блокировки, понапрасну расходует процессорное время, так как находится в busy loop.
6. Двойной захват спин-блокировки приводит к deadlock.
7. Можно использовать в обработчиках прерывания. Но если одна и та же спин-блокировка используется и в процессе, и в обработчике прерывания, то при захвате в процессе
необходимо запрещать локальные прерывания. Иначе может произойти deadlock:
```cpp
Поток A
Захват sl
Выполнение кр. секции
                              Прерывание
                              Захват sl
                              Ожидание освобождения sl  
---------------
Как следствие, deadlock.

```

Использование спин-блокировки:

```cpp
DEFINE_SPINLOCK(mr_lock);
spin_lock(&mr_lock);
/* Критический участок кода ... */
spin_unlock(&mr_lock);
```

> Зачем использовать spinlock в прерываниях: чтобы поток на другом ядре не получил доступ к данным.

На однопроцессорных системах код, связанный со спинблокировкой, не компилируется(просто запрещается preempt). 

В обработчике прерываний перед захватом спин-блокировки нужно запрещать все локальные прерывания, так как другой обработчик может захватить ту же самую блокировку [видимо речь идет о других обработчиках прерываний, использующих ту же блокировку] - как итог deadlock.

Нет необходимости запрещать прерывания на другом процессоре. В этом случае код не вытеснится, а просто будет ожидать, пока первый процессор не освободит спин-блокировку.

Запрет локальных прерываний и захват спин-лока:

```cpp
DEFINE_SPINLOCK(mr_lock);
unsigned long flags;
spin_lock_irqsave(&mr_lock, flags);
/* Критический участок кода... */
spin_unlock_irqrestore(&mr_lock, flags);
```

Важно, чтоб перед выполнением spin_lock_irqsave прерывания были разрешены. Иначе spin_unlock_irqrestore восстановит первоначальное состояние системы прерываний - они будут так же запрещены.

```cpp
spin_lock_init(); // Инициализация переменной spinlock_t
spin_trylock(); // попытка захвата блокировки, если не захвачена, возвращается 0
```

1. Так как процесс может быть вытеснен нижней половиной обработчика прерывания и если данные используются и в процесе, и в нижней половине, то нужно захватить блокировку и запретить запуск нижних половин:
```cpp
spin_lock_bh();
spin_unlock_bh();
```
2. Так как нижняя половина может быть вытеснена hw-прерыванием, то перед захватом данных в нижней половине(если эти данные могут использоваться в hw-прерывании) нужно запретить прерывания на процессоре: `spin_lock_irqsave()`.
3. Данные, используемые только в тасклетах, не нужно защищать, так как два одинаковых тасклета не могут выполняться параллельно. Если данные используются в другом тасклете, данные нужно защищать.
4. В softirq данные необходимо защищать, так как обработчики могут выполняться параллельно.

### rw-spinlock

Если работа со структурой данных может быть четко разделена на этапы чтения/записи, то лучше использовать rw-spinlock. При чтении - параллельный доступ к данным, при записи - монопольный. 

```cpp
DEFINE_RWLOCK(mr_rwlock);
read_lock(&mr_rwlock);
read_unlock(&mr_rwlock);

write_lock(&mr_rwlock);
write_unlock(&mr_lock);
```

А здесь будет deadlock:
```cpp
read_lock (&mr_rwlock);
write_lock(&mr_rwlock);
```

Блокировка по чтению имеет больший приоритет с блокировкой по записи. Так, если некоторый поток удерживает блокировку по чтению, а другой поток ожидает ее освобождения, чтобы получить монопольный доступ к ресурсу по записи, то все другие потоки, пытающиеся захватить блокировку по чтению, будут без проблем добиваться своей
цели. Поток записи, который периодически проверяет на освобождение блокировки, не сможет ее захватить, пока все потоки чтения не освободят эту блокировку.

## Семафоры

1. Семафоры - при попытке захвата занятого семафора, поток помещается в очередь ожидания(wait queue) и замораживается, после этого процессор переходит к выполнению другой задачи.
2. Хорошо подходят для длительного удержания (из-за смены контекста).
3. Нельзя использовать в прерываниях, потому что в контексте прерывания потоки(поток, выполняющий irq) не обрабатываются планировщиком. Следовательно, захваченный семафор не будет иметь влияния на изменение данных в прерывании.
4. Нельзя захватывать семафор, если перед этим был захвачен spinlock. Иначе если семафор уже захвачен, то процесс перейдет в состояние ожидания - при спинлоке вытеснение запрещено, поэтому задача не заснет, а продолжит выполнение.
5. Процесс, который захватил семафор, может быть вытеснен. Но это не проблема.

Семафоны бывают двух видов: счетные(count > 1) и бинарные(count = 1). При инициализации семафона можно задать count. Если count > 1, то его могут удерживать count потоков, при этом нельзя говорить о монопольном доступе. Счетные семафоры обычно не используются в ядре, но могут решать задачу ограничения количества одновременного доступа к ресурсу: не более count.

Для семафоров есть две операции: down() - уменьшение счетчика на 1 и up() - увеличение счетчика на 1.
1. Если после down() count >= 0, то семафор захватывается успешно - можно выполнить критический участок кода.
2. Если полученное после down значение отрицательно, то поток помещается в очередь ожидания.
3. После успешного down() происходит up().

Создание семафора:
```
struct semaphore name;
sema_init(&name, count);
```

Для захвата семафора:
```cpp
down_interruptible(); // попытка заахватить семафор. Если попытка неудачная, то процесс переводится в состояние TASK_INTERRUPTIBLE
down(); // аналогично down_interruptible, но процесс переходит в TASK_UNINTERRUPTIBLE. Нельзя разбудить с помощью сигнала.
down_trylock(); // попытка захвата, если неудачно - процесс не блокируется
up(); // освобождение захваченного семафора
```

Аналогично с spinlock, если rw semaphore.

Напрямую счетные семафоры используются редко. Вот пример задачи, которая может быть решена:
Есть два типа процессов: производители - пишут что-то в буфер, потребители - читают из буфера.
Процессы производители для записи в буфер опускают семафор. Если семафор = 0, то буфер полон и нужно подождать. Если значение семафора равно максимальному значению счетчика, то потребитель ждет, пока значение не уменьшится.

## Мьютексы

Мьютекс представляется в виде структуры mutex. Он ведет себя так же, как и семафор, счетчик использования которого равен единице, но имеет более простой интерфейс,
более высокую эффективность и налагает дополнительные ограничения при использовании.

Создание:

```cpp
DEFINE_MUTEX(name); // статически
mutex_init(&mutex); // динамически
```

Захват и освобождение:

```cpp
mutex_lock(&mutex); // захват
mutex_unlock(&mutex); // освобождение
mutex_trylock(&mutex); // попытка захватат без блокировки, если захвачен возвращает 1, если нет - 0.
mutex_is_locked(&mutex); // возвращает 1, если уже захвачен, 0 если нет
```

Ограничения на мьютексы:
1. В один и тот же момент времени мьютекс может удерживать только одна задача.
2. Тот процесс, который захватил мьютекс, должен обязательно его освободить. Нельзя захватить мьютекс в одном контексте, а затем освободить его в другом.
3. Повторные захваты и освобождения мьютексов не разрешаются.
4. Процесс не может завершить свою работу до тех пор, пока он не освободит мьютекс.
5. Мьютекс нельзя захватить в обработчике прерываний или в его нижней половине, даже с помощью функции mutex_trylock().
6. Для работы с мьютексами может использоваться только официальное API.

За всеми этими ограничениями можно следить, если задан `CONFIG_DEBUG_MUTEXES` - вывод warning.

Мьютексы нужно использовать, когда время удержания большое. Или во время удержания блокировки процесс может переходить в состояние ожидания.

> Основное отличие бинарного семафора от мьютекса: если блокировка в состоянии 0(никакой другой поток не может захватить ее), то для освобождения блокировки:
> 1. Для мьютекса это должен сделать поток, который захватил указанную блокировку. Если это попробует сделать другой поток, то тут зависит от реализации мьютекса.
> 2. Для семафора: возможно, то есть семафор может освободить любой из потоков.

## Условные переменные
Так же, как и при использовании мьютекса, ставяются в очередь.

Условные переменные (completion variable) — простое средство синхронизации между двумя задачами в ядре, когда необходимо, чтобы одна задача отправила сигнал другой
о том, что произошло некоторое событие. С помощью условной переменной одна задача сообщает системе, что она переходит в состояние ожидания до тех пор, пока другая задача не выполнит некоторую работу. Когда вся нужная работа будет выполнена, другая задача с помощью условной переменной уведомляет об этом систему и та возвращает к выполнению все ожидающие задачи.

Представлены в виде структуры `completion`.

Создание:
```cpp
DECLARE_COMPLETION(mr_comp); // статически
init_completion(); // динамически
```

Взадимодействие:
```cpp
wait_for_completion(); // перевод с состояние ожидания, пока другой процесс не сделает complete()
complete(); // сигнализация всем ожидающим задачам, что действие выполнено.
```
## Барьеры памяти

И компилятор и процессор могут менять порядок выполнения операций. Компилятор это делает для оптимизации кода, процессор делает например в случае out of order. Так как ни компилятор, ни процессор понятия не имеют, что работа с переменными может осуществляться в другом контексте(другой процессор или другая машина), то возникает необходимость запретить переупорядочивание команд записи или чтения.

`rmb()` - барьер на чтение. Гарантирует, что команды чтения до барьера не будут переставлены с командами чтения после барьера.

`wmb()` - барьер на чтение. Гарантирует, что команды записи до барьера не будут переставлены с командами записи после барьера.

`mb()` - барьер для памяти и для чтения одновременно. Никакие rw-команды до барьера не будут переставлены с rw-командами после барьера.

`read_barrier_depends()` - все операции чтения до барьера не будут переставлены с операциями чтения после барьера в случае, если они зависят друг от друга. Обычно выполняется быстрее, чем rmb.

Пример:

```c
Поток 1                      Поток 2
a = 3;                       -
mb();                        –
b = 4;                       c = b;
–                            rmb();
–                            d = a;
```
Предоположим, что изначально a = 1 и b = 2. Тут может сложится ситуация, что без барьеров в `c` запишется новое значение 4, а в `d` запишется старое значение 1.

Макросы `smp_rmb()`, `smp_wmb()`, `smp_mb()` и `smpread_barrier_depends()`: для SMP-систем это просто барьеры памяти, а для однопроцессорной системы только барьер для компилятора (подстановка `barrier()`).

`barrier()` - барьер для чтения и записи только для компилятора.


## Userspace multithread

В userspace можно использовать pthreads(POSIX Threads) — стандарт POSIX-реализации потоков (нитей) выполнения. Стандарт определяет единый API для управления потоками, их синхронизации и планирования.

```c
#include <pthread.h>
```

Компиляция происходит с добавлением флага `-pthread`.

Основные типы:
```c
pthread_t thread; // thread
pthread_mutex_t mutex; // mutex
pthread_spinlock_t lock; // spinlock
```

Основные функции:
```c
pthread_create(); // создание потока.
pthread_exit(); // завершение потока (должна вызываться функцией потока при завершении).
pthread_cancel(); //
pthread_join(); // подключиться к другому потоку и ожидать его завершения; поток, к которому необходимо подключиться, должен быть создан с возможностью подключения
pthread_detach(); // отключиться от потока, сделав его при этом отдельным
```
